# Tasker — простой таск-трекер

## Обзор

Tasker — веб-приложение для управления задачами командами в изолированных рабочих пространствах (workspaces). Задачи отображаются в виде канбан-доски и списка, могут одновременно находиться в нескольких проектах (с собственным статусом в каждом), содержат срок, приоритет, ответственного, описание, вложения и комментарии. В перспективе — интеграция с GitHub (автоматическая привязка задач к Pull Request) и встроенный раздел проектной документации, которую удобно прикреплять к задачам и редактировать в одном месте.

## Основные возможности

### Пользователи и доступы
- **Администратор (admin)** — глобальная роль, владелец всего ресурса: управление пользователями и всеми пространствами.
- **Владелец пространства (workspace owner)** — создаёт пространство, приглашает пользователей и выдаёт/отзывает им доступ.
- **Обычный пользователь (member)** — работает с задачами в пространствах, к которым ему выдан доступ.
- Приглашения в пространство (по email/ссылке), управление участниками.

### Проекты и задачи
- Пространство содержит проекты; у каждого проекта свой упорядоченный набор статусов (колонок) с категорией (к выполнению / в работе / готово) и цветом. Новый проект получает три статуса по умолчанию.
- Создавать проекты и настраивать статусы может владелец пространства; участникам он выдаёт право «Управление проектами» индивидуально.
- Задача принадлежит пространству и может быть размещена **в нескольких проектах одновременно**, при этом в каждом проекте у неё свой статус и позиция на доске.
- Поля задачи: название, описание, срок выполнения (due date), приоритет, ответственный (assignee), проекты + статус в каждом.
- Вложения (файлы) к задачам.
- Комментарии к задачам.

### Представления
- **Канбан-доска** проекта: колонки = статусы, drag-and-drop между колонками и внутри колонки.
- **Список**: табличное представление с сортировкой и фильтрами (статус, приоритет, ответственный, срок).

### Планируется
- **Интеграция с GitHub**: GitHub App + webhooks, автоматическая привязка задач к PR по идентификатору задачи в названии ветки/PR/коммите, отображение статуса PR в задаче.
- **Проектная документация**: отдельный раздел пространства с иерархией страниц, rich-text редактором, привязкой документов к задачам (M:N).

## Технологический стек

- **Язык программирования:** TypeScript
- **Фреймворк:** Next.js (App Router) — full-stack монолит: React UI, Server Components, Server Actions / Route Handlers
- **База данных:** PostgreSQL
- **ORM:** Prisma
- **Аутентификация:** Better Auth (1.7) с Prisma-адаптером; вход по email + паролю, сессии в БД (cookie); плагин `admin` — глобальная роль (`user` / `admin` в поле `User.role`), первый администратор назначается через `ADMIN_EMAILS`; плагин `organization` — пространства, участники, роли и приглашения (этап «Рабочие пространства»); GitHub OAuth — вместе с интеграцией GitHub
- **UI:** Tailwind CSS + shadcn/ui; канбан — `@dnd-kit/core` + `@dnd-kit/sortable` (перетаскивание указателем, касанием и с клавиатуры); Tiptap (предлагается) для rich-text (описания задач, документация); пока описание задачи — простой текст
- **Порядок карточек:** `fractional-indexing` (дробные ключи, колонка `TaskPlacement.position` с `COLLATE "C"`)
- **Валидация:** Zod (общие схемы для форм и серверных обработчиков)
- **Хранение файлов:** S3-совместимое хранилище через `@aws-sdk/client-s3`. Локально — MinIO (образ `pgsty/minio`, официальные образы больше не публикуются). Загрузка по presigned URL
- **Почта:** SMTP через nodemailer (`src/shared/mail`); локально — Mailpit (SMTP 1025, UI 8025) в docker-compose. Используется для приглашений в пространство
- **Инфраструктура разработки:** pnpm, docker-compose (Postgres 17 на порту 5433, MinIO, Mailpit), Prisma 7 с `@prisma/adapter-pg`, pino, Vitest, ESLint + Prettier, husky + lint-staged
- **Интеграции:** GitHub (Octokit, GitHub App, webhooks) — в будущем

## Архитектурные заметки

- **Мультиарендность через workspace**: каждая доменная сущность (проект, задача, документ) принадлежит пространству; все запросы к данным обязательно фильтруются по `workspaceId` и проверяются на членство пользователя.
- **Двухуровневая модель ролей**: глобальная роль пользователя (`ADMIN` / `USER`) + роль участника в пространстве (`OWNER` / `MEMBER`). Проверка доступа централизована в слое авторизации, а не разбросана по UI.
- **Задача ↔ проект — связь M:N** через отдельную сущность размещения (`TaskPlacement`: `taskId`, `projectId`, `statusId`, `position`). Статус и порядок на доске хранятся в размещении, а не в самой задаче.
- **Статусы — данные, а не enum**: у каждого проекта настраиваемый упорядоченный набор статусов.
- **Порядок карточек** — дробные/lexorank-позиции, чтобы перемещение карточки обновляло одну строку.
- **Документы** — отдельная сущность пространства с контентом в JSONB (формат Tiptap) и M:N-связью с задачами.
- **GitHub** — изолированный модуль интеграции: webhook-эндпоинт с проверкой подписи, сущность связи `TaskPullRequest`; ядро задач не зависит от GitHub.
- Бизнес-логика вынесена из React-компонентов и route-обработчиков в серверные сервисы/use-cases.

## Нефункциональные требования

- **Логирование:** структурированные логи, уровень настраивается через `LOG_LEVEL`.
- **Обработка ошибок:** единый формат ошибок для Server Actions/API (код + сообщение), доменные ошибки отделены от инфраструктурных.
- **Безопасность:**
  - проверка прав на каждом серверном действии (workspace membership + роль), защита от IDOR;
  - валидация всех входных данных (Zod);
  - безопасная загрузка файлов: ограничение размера и типа, приватные бакеты, presigned URL с коротким сроком жизни;
  - приглашения — одноразовые токены с истечением срока;
  - проверка подписи GitHub webhook (`X-Hub-Signature-256`), секреты только в переменных окружения;
  - санитизация rich-text контента при рендеринге (XSS).
- **Производительность:** индексы по `workspaceId`, `projectId`, `assigneeId`, `dueDate`; пагинация списков.
