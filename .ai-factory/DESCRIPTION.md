# Tasker — простой таск-трекер

## Обзор

Tasker — веб-приложение для управления задачами командами в изолированных рабочих пространствах (workspaces). Задачи отображаются в виде канбан-доски и списка, могут одновременно находиться в нескольких проектах (с собственным статусом в каждом), содержат срок, приоритет, ответственного, описание, вложения и комментарии. В перспективе — интеграция с GitHub (автоматическая привязка задач к Pull Request) и встроенный раздел проектной документации, которую удобно прикреплять к задачам и редактировать в одном месте.

## Основные возможности

### Пользователи и доступы
- **Администратор (admin)** — глобальная роль, владелец всего ресурса: управление пользователями и всеми пространствами.
- **Владелец пространства (workspace owner)** — создаёт пространство, приглашает пользователей и выдаёт/отзывает им доступ.
- **Обычный пользователь (member)** — работает с задачами в пространствах, к которым ему выдан доступ.
- Приглашения в пространство (по email/ссылке), управление участниками.

### Проекты и задачи
- Пространство содержит проекты; у каждого проекта свой упорядоченный набор статусов (колонок) с категорией (к выполнению / в работе / готово) и цветом. Новый проект получает три статуса по умолчанию.
- Создавать проекты и настраивать статусы может владелец пространства; участникам он выдаёт право «Управление проектами» индивидуально.
- Задача принадлежит пространству и может быть размещена **в нескольких проектах одновременно**, при этом в каждом проекте у неё свой статус и позиция на доске.
- Поля задачи: название, описание, срок выполнения (due date), приоритет, ответственный (assignee), проекты + статус в каждом.
- Подзадачи любой вложенности (до 10 уровней): подзадача — обычная задача с родителем; по умолчанию не на доске, по желанию выводится в проект на нужный статус. Прогресс «выполнено N из M», смена родителя с защитой от циклов, удаление родителя удаляет поддерево.
- Вложения (файлы) к задачам.
- Комментарии к задачам с @упоминаниями участников (подсказка после `@`).

### Профили и уведомления
- Профиль пользователя: фото, имя, должность, описание; страница аккаунта (email, дата регистрации, роль, пространства).
- Публичный профиль участника внутри пространства (роль, дата вступления, статистика и открытые задачи) и карточка при наведении на ответственного, автора комментария или упоминание.
- Уведомления в приложении (колокольчик, страница `/notifications`) и по email: упоминание, назначение ответственным, комментарий к моей задаче, приглашение в пространство. Каналы настраиваются по каждому типу события в профиле.

### AI-агенты (MCP)
- Агенты пространства: владелец создаёт служебного участника («Claude — backend») с правами, ответственным и своими токенами; агент — автор своих задач, комментариев и документов (метка «Агент», робот вместо фото), его можно назначить и упомянуть, уведомления агента получает ответственный; войти в интерфейс агент не может; отключение отзывает токены и снимает членство.
- Личные токены доступа в профиле: токен действует в одном пространстве с правами владельца, без админских прав; созданное через него помечается «через Claude Code»; срок, отзыв, в БД — только хеш.
- Области токена: `read` (всегда), `tasks`, `documents` — инструменты вне областей агенту не показываются.
- Журнал действий MCP (что, когда, каким токеном) — у агента для владельца пространства, у личного токена для его владельца; хранится 90 дней.
- MCP-сервер `/api/mcp` для Claude Code: просмотр и поиск задач, создание задач и подзадач, правка полей, смена статуса и родителя, комментарии с @упоминаниями, вложения; документы — поиск, чтение заметок и файлов, заметки с защитой версией, загрузка файлов, папки, теги, связи с задачами.
- Агент знает правила интеграции с GitHub пространства (ключ задачи в ветке, коммитах и PR, подключённые репозитории, автосмена статуса), проверяет текст ветки/PR тем же разбором, что и вебхук; сценарии `start_task` / `finish_task`.

### Документы пространства
- У каждого пространства своё файловое хранилище с квотой (`DOCUMENTS_WORKSPACE_QUOTA_MB`, по умолчанию 1 ГБ): папки и подпапки (до 8 уровней), теги, поиск по названию, тегу и виду.
- Markdown-заметки (GFM: таблицы, чек-листы) с редактором (панель форматирования, предпросмотр, «Рядом») и безопасным рендером; защита от одновременной правки по версии.
- Загруженные файлы до 50 МБ с просмотром в приложении: изображения, PDF, текст и код, Markdown, CSV/TSV, JSON, аудио, видео; остальное — скачивание.
- Документы привязываются к задачам (M:N): раздел «Документы» в задаче и блок «Задачи» в документе.
- Читают и привязывают все участники; создают и меняют — владелец и участники с правом «Управление документами».

### Представления
- **Канбан-доска** проекта: колонки = статусы, drag-and-drop между колонками и внутри колонки.
- **Список**: табличное представление с сортировкой и фильтрами (статус, приоритет, ответственный, срок).

### Планируется
- **Интеграция с GitHub**: GitHub App + webhooks, автоматическая привязка задач к PR по идентификатору задачи в названии ветки/PR/коммите, отображение статуса PR в задаче.
## Технологический стек

- **Язык программирования:** TypeScript
- **Фреймворк:** Next.js (App Router) — full-stack монолит: React UI, Server Components, Server Actions / Route Handlers
- **База данных:** PostgreSQL
- **ORM:** Prisma
- **Аутентификация:** Better Auth (1.7) с Prisma-адаптером; вход по email + паролю, сессии в БД (cookie); плагин `admin` — глобальная роль (`user` / `admin` в поле `User.role`), первый администратор назначается через `ADMIN_EMAILS`; плагин `organization` — пространства, участники, роли и приглашения (этап «Рабочие пространства»); GitHub OAuth — вместе с интеграцией GitHub; подтверждение email по письму (`AUTH_REQUIRE_EMAIL_VERIFICATION`), сброс и смена пароля, плагин `twoFactor` (TOTP + резервные коды, QR — пакет `qrcode` в браузере), список активных сессий в профиле; rate limit Better Auth в БД (`RateLimit`) и свой лимитер Server Actions (`src/shared/rate-limit`, `ActionRateLimit`), IP — из `X-Forwarded-For`
- **UI:** Tailwind CSS + shadcn/ui; канбан — `@dnd-kit/core` + `@dnd-kit/sortable` (перетаскивание указателем, касанием и с клавиатуры); документы — Markdown (`react-markdown` + `remark-gfm`, сырой HTML не рендерится), редактор — текстовое поле с панелью форматирования; описание задачи — простой текст
- **Порядок карточек:** `fractional-indexing` (дробные ключи, колонка `TaskPlacement.position` с `COLLATE "C"`)
- **Валидация:** Zod (общие схемы для форм и серверных обработчиков)
- **Хранение файлов:** S3-совместимое хранилище через `@aws-sdk/client-s3`. Локально — MinIO (образ `pgsty/minio`, официальные образы больше не публикуются). Загрузка из браузера напрямую в хранилище по presigned POST (`@aws-sdk/s3-presigned-post`), скачивание — по presigned GET (`@aws-sdk/s3-request-presigner`) через проверку доступа; `S3_PUBLIC_ENDPOINT` — адрес хранилища для браузера, CORS MinIO — `MINIO_API_CORS_ALLOW_ORIGIN`. Вложения: до 25 МБ, типы по allowlist расширений, до 20 файлов на задачу и 10 на комментарий. Документы: до 50 МБ, квота пространства, ключи `ws/<workspaceId>/docs/<uuid>`
- **Почта:** SMTP через nodemailer (`src/shared/mail`); локально — Mailpit (SMTP 1025, UI 8025) в docker-compose. Используется для приглашений в пространство
- **Инфраструктура разработки:** pnpm, docker-compose (Postgres 17 на порту 5433, MinIO, Mailpit), Prisma 7 с `@prisma/adapter-pg`, pino, Vitest, ESLint + Prettier, husky + lint-staged
- **Развёртывание:** один VPS (`https://tracker.plwedding.ru`) с docker compose: Postgres и MinIO на том же сервере, общий edge-прокси Caddy (HTTPS, Let's Encrypt), образы в GHCR, CD из GitHub Actions по SSH; почта — SMTP ящика на домене (`docs/production.md`)
- **Интеграции:** GitHub — пакет `octokit` (GitHub App: токены установок, пользовательские токены), webhooks; GitHub App создаёт администратор из админки по манифесту (ключи в БД, зашифрованы) или задаёт переменными `GITHUB_*` (все или ни одной), модуль `src/modules/integrations/github`; MCP — `@modelcontextprotocol/sdk` (Streamable HTTP без сессий, JSON-ответы), модули `agents`, `api-tokens` и `agent-mcp`

## Архитектурные заметки

- **Мультиарендность через workspace**: каждая доменная сущность (проект, задача, документ) принадлежит пространству; все запросы к данным обязательно фильтруются по `workspaceId` и проверяются на членство пользователя.
- **Двухуровневая модель ролей**: глобальная роль пользователя (`ADMIN` / `USER`) + роль участника в пространстве (`OWNER` / `MEMBER`). Проверка доступа централизована в слое авторизации, а не разбросана по UI.
- **Подзадачи** — самосвязь `Task.parentId` (составной FK с `workspaceId`, каскад); дерево читается рекурсивными CTE, изменения дерева — под advisory-блокировкой пространства.
- **Задача ↔ проект — связь M:N** через отдельную сущность размещения (`TaskPlacement`: `taskId`, `projectId`, `statusId`, `position`). Статус и порядок на доске хранятся в размещении, а не в самой задаче.
- **Статусы — данные, а не enum**: у каждого проекта настраиваемый упорядоченный набор статусов.
- **Порядок карточек** — дробные/lexorank-позиции, чтобы перемещение карточки обновляло одну строку.
- **Документы** — сущность пространства двух видов: заметка (Markdown в `Document.content`) и файл (объект S3 под префиксом `ws/<workspaceId>/docs/`); папки (дерево), теги и M:N-связь с задачами (`TaskDocumentLink`).
- **GitHub** — изолированный модуль интеграции: webhook-эндпоинт с проверкой подписи, сущность связи `TaskPullRequest`; ядро задач не зависит от GitHub.
- **Агенты (MCP)** — bearer-токен превращается в сессию владельца (роль `user`) только в `/api/mcp`; инструменты вызывают те же сервисы, что Server Actions, пространство берётся из токена. Агент пространства — служебный `User` (`isAgent`, без `Account`, сессия запрещена хуком Better Auth) + `WorkspaceAgent`; членство агента модуль `agents` пишет в обход плагина `organization`. Сессия токена несёт `via` (токен, области, агент): по нему ставится пометка «через агента» (`createdViaTokenId`) и проверяются области; изменения пишутся в журнал `McpActivity`.
- Бизнес-логика вынесена из React-компонентов и route-обработчиков в серверные сервисы/use-cases.

## Нефункциональные требования

- **Логирование:** структурированные логи, уровень настраивается через `LOG_LEVEL`.
- **Обработка ошибок:** единый формат ошибок для Server Actions/API (код + сообщение), доменные ошибки отделены от инфраструктурных.
- **Безопасность:**
  - проверка прав на каждом серверном действии (workspace membership + роль), защита от IDOR;
  - валидация всех входных данных (Zod);
  - безопасная загрузка файлов: ограничение размера и типа, приватные бакеты, presigned URL с коротким сроком жизни;
  - приглашения — одноразовые токены с истечением срока;
  - проверка подписи GitHub webhook (`X-Hub-Signature-256`), секреты только в переменных окружения;
  - санитизация rich-text контента при рендеринге (XSS).
- **Производительность:** индексы по `workspaceId`, `projectId`, `assigneeId`, `dueDate`; пагинация списков.
