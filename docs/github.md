# Интеграция с GitHub

Tasker связывает задачи с работой в GitHub. Ключ задачи (`TSK-42`) в названии ветки, в заголовке или описании PR или в тексте коммита привязывает их к задаче. В задаче видны PR (состояние, ревью, CI), ветки и коммиты, на доске и в списке — значок PR. Проект может сам двигать задачу по статусам, когда PR открывают и сливают.

Интеграция необязательна. Пока GitHub App не создан, Tasker работает как раньше: привязки GitHub-аккаунта нет, вебхук отвечает 404, а в настройках пространства вместо подключения — подсказка, что это делает администратор.

GitHub App одно на весь Tasker. Его один раз создаёт администратор ресурса — в **Админка → Интеграции** (см. [Создание GitHub App](#создание-github-app)). Дальше любой владелец пространства сам подключает свои аккаунты, организации и репозитории из интерфейса.

## Как это выглядит для пользователя

1. Владелец пространства привязывает GitHub в профиле (`/profile/account`) и подключает GitHub App в **Настройки → Интеграция с GitHub** (`/w/<slug>/settings/github`).
2. Там же он выбирает репозитории пространства. События приходят только из выбранных репозиториев.
3. Разработчик называет ветку `tsk-42-login` или пишет `TSK-42` в PR или коммите. Связь появляется в разделе **GitHub** задачи.
4. В настройках проекта (**GitHub**) можно выбрать статус для «PR открыт» и для «PR слит».

## Ключ задач

| Что | Как |
|-----|-----|
| Где хранится | `Workspace.taskKey`: 2–10 символов, латинская буква, затем буквы и цифры, верхний регистр, уникален глобально |
| Как задаётся | При создании пространства (поле «Ключ задач», по умолчанию — из названия: «Отдел продаж» → `OP`) или в настройках пространства |
| Где виден | Везде вместо `#42`: карточки, список, задача, уведомления. Адреса не меняются (`/w/<slug>/tasks/42`) |
| Поиск | Список задач ищет по `42`, `#42` и `TSK-42` |
| Смена ключа | Ветки и PR со старым ключом перестают распознаваться, уже созданные связи остаются |

Существующим пространствам ключ проставила миграция `add_workspace_task_key` (из slug).

## Что привязывается

| Источник | Что связывается с задачей |
|----------|---------------------------|
| Имя ветки PR, заголовок, описание | PR (автосвязь) |
| Имя ветки в `push` / `create` | Ветка и все коммиты этого push |
| Текст коммита в `push` | Только этот коммит |
| Ссылка `https://github.com/owner/repo/pull/12` в разделе GitHub задачи | PR (ручная связь) |

Правила распознавания:

- `KEY-N` на границах слова, без учёта регистра: `tsk-42-fix`, `[TSK-42]`, `feature/TSK-42`, `TSK-42:`. Не подходят `TSK-012`, `TSK-12abc`, `2TSK-1`.
- Ссылка срабатывает, только если ключ совпадает с ключом пространства, где выбран репозиторий. Один репозиторий может обслуживать несколько пространств, ссылки различает ключ.
- Из одного события разбирается не больше 50 ссылок. GitHub кладёт в `push` не больше 20 коммитов, а за остальными Tasker в API не ходит.
- При правке PR автосвязи пересчитываются: исчезнувшая из текста ссылка снимает связь.
- **Отвязать** (иконка у PR) отмечает связь как отвязанную вручную: автоматика её больше не восстановит. Ручную связь автоматика не снимает. Ручная привязка того же PR восстанавливает связь.
- Ручная привязка требует, чтобы репозиторий был выбран в пространстве: PR загружается токеном установки.

## Состояние PR

| Поле | Значения | Откуда |
|------|----------|--------|
| Состояние | Открыт, Черновик, Слит, Закрыт | `pull_request` |
| Ревью | Одобрен, Нужны изменения | Последнее ревью каждого ревьюера. Комментарий после одобрения его не отменяет, снятое ревью — отменяет |
| CI | выполняется, пройден, упал | `check_suite` последнего коммита PR: упавший важнее незавершённого, отменённые и пропущенные не учитываются |

На карточке видно самое заметное состояние среди PR задачи (открыт > черновик > слит > закрыт) и их число.

## Автосмена статуса

В **настройках проекта → GitHub** два селекта: «Когда PR открыт или готов к ревью» и «Когда PR слит». Статусы — только этого проекта, нужно право «Управление проектами».

- Статус меняется **только вперёд** по категории (`todo` → `in_progress` → `done`). Слитый PR не вернёт задачу из «Готово», повторное открытие не откатит её назад.
- Черновик и закрытие без слияния статус не меняют.
- Задача в нескольких проектах меняет статус в каждом по его настройке.
- Новой связи с уже открытым или слитым PR применяется его текущее состояние.
- Удалённый статус сбрасывает настройку (`SetNull`).

## Уведомления

Новые типы в профиле (**Уведомления**), каналы — в приложении и письмом:

| Тип | Кому | Письмо по умолчанию |
|-----|------|---------------------|
| `pr_linked` — к задаче привязан PR | Ответственному задачи | нет |
| `pr_merged` — PR задачи слит | Ответственному задачи | нет |
| `pr_review` — PR одобрили или запросили изменения | Автору PR, если его GitHub привязан и он участник пространства | да |

Автор действия — пользователь Tasker с привязанным GitHub (иначе в тексте логин `@login`). Себе уведомление не отправляется.

## Привязка аккаунта GitHub

- **Войти через GitHub нельзя**: вход в Tasker — только через plwedding ID. OAuth GitHub App нужен, чтобы привязать аккаунт GitHub (авторство PR, коммитов и ревью) и получить токен пользователя. Начать вход с провайдером `github` (`/api/auth/sign-in/social`) — `403 SIGN_IN_PROVIDER_NOT_ALLOWED`.
- Привязка — явная, в `/profile/account` (`linkSocial`); по email GitHub к пользователю не привязывается. Email GitHub может отличаться от рабочего (`allowDifferentEmails`).
- OAuth-токены пользователей хранятся зашифрованными (`encryptOAuthTokens`). Истёкший токен GitHub App обновляет Better Auth (`getAccessToken`).

## Подключение установки

GitHub возвращает пользователя на Setup URL с `installation_id`. Этому параметру нельзя доверять, поэтому подключение проверяет:

1. Подписанный `state` из ссылки установки: HMAC-SHA256 на ключе, выведенном из `BETTER_AUTH_SECRET` (HKDF). Он содержит пространство и пользователя и живёт 10 минут.
2. Пользователь — владелец пространства, его GitHub привязан.
3. Установка есть в `GET /user/installations` этого пользователя (запрос его токеном).

Только после этого Tasker сохраняет установку и её репозитории (`GET /installation/repositories` токеном установки) и связывает её с пространством. Уже установленное приложение подключается из списка «Добавить установку» без переустановки.

| Действие | Что происходит |
|----------|----------------|
| Выключить репозиторий | Удаляются связи задач пространства с его PR, ветками и коммитами |
| Отключить установку | То же для всех её репозиториев; на GitHub приложение остаётся |
| Удалить приложение на GitHub (`installation.deleted`) | Установка, репозитории, PR и все связи удаляются каскадом |
| Приостановить (`suspend`) | События её репозиториев не обрабатываются до `unsuspend` |

## Создание GitHub App

### Из админки (рекомендуется)

1. Войдите администратором и откройте **Админка → Интеграции** (`/admin/integrations`).
2. Укажите название (уникально на всём GitHub, до 34 символов) и где создать приложение: в личном аккаунте или в организации (нужны права владельца организации).
3. Оставьте **Разрешить установку любым аккаунтам**: иначе приложение установится только на аккаунт его владельца, и другие владельцы пространств не смогут подключить свои репозитории.
4. Нажмите **Создать GitHub App на GitHub**. GitHub откроет готовое приложение по [манифесту](https://docs.github.com/apps/sharing-github-apps/registering-a-github-app-from-a-manifest): адреса, права и события уже заполнены. Нажмите **Create GitHub App**.
5. GitHub вернёт на `/api/integrations/github/manifest`: Tasker обменяет одноразовый код на ключи и сохранит их в БД (`GithubAppConfig`, секреты — AES-256-GCM, ключ из `BETTER_AUTH_SECRET`). Интеграция и привязка GitHub-аккаунта включаются сразу, без перезапуска.
6. Право пользователя **Email addresses** манифест не принимает. Включите его вручную: ссылка «Настройки приложения на GitHub» в админке → **Account permissions → Email addresses: Read-only** → **Save changes**. Без него привязка не получит email пользователя со скрытым адресом.

Если `BETTER_AUTH_URL` — `localhost` или адрес частной сети, вебхук GitHub не принимает: приложение создаётся без него (см. [Локальная разработка](#локальная-разработка)).

**Отключить** в админке удаляет ключи из Tasker; приложение на GitHub остаётся, удалите его там при необходимости. Ссылка на создание действует час и только для начавшего её администратора. После смены `BETTER_AUTH_SECRET` сохранённые ключи не расшифровать — создайте приложение заново.

Переменные `GITHUB_*` важнее записи из админки: если они заданы, админка только сообщает об этом.

### Вручную, через переменные окружения

**GitHub → Settings → Developer settings → GitHub Apps → New GitHub App** (или в настройках организации). Чтобы приложение могли устанавливать другие аккаунты, выберите **Any account** в «Where can this GitHub App be installed?».

| Поле | Значение |
|------|----------|
| Homepage URL | `https://tracker.plwedding.ru` (локально `http://localhost:3000`) |
| Callback URL | `<BETTER_AUTH_URL>/api/auth/callback/github` |
| Request user authorization (OAuth) during installation | выключено |
| Setup URL | `<BETTER_AUTH_URL>/api/integrations/github/setup`, включить **Redirect on update** |
| Webhook URL | `<BETTER_AUTH_URL>/api/webhooks/github` |
| Webhook secret | случайная строка от 16 символов (`openssl rand -hex 32`) → `GITHUB_WEBHOOK_SECRET` |

Права (Repository permissions — Read-only):

| Право | Зачем |
|-------|-------|
| Metadata | Обязательно |
| Contents | События `push`, `create`, `delete` |
| Pull requests | События PR и ревью, ручная привязка |
| Checks | Событие `check_suite` |
| Account permissions → Email addresses | Email при привязке GitHub-аккаунта |

События (Subscribe to events): **Pull request**, **Pull request review**, **Push**, **Create**, **Delete**, **Check suite**. События `installation` и `installation_repositories` приходят всегда.

После создания:

1. **App ID** → `GITHUB_APP_ID`, slug из адреса `github.com/apps/<slug>` → `GITHUB_APP_SLUG`.
2. **Client ID** и **Generate a new client secret** → `GITHUB_APP_CLIENT_ID`, `GITHUB_APP_CLIENT_SECRET`.
3. **Generate a private key** (`.pem`) → `GITHUB_APP_PRIVATE_KEY` одной строкой:

```bash
awk 'NF {sub(/\r/, ""); printf "%s\\n", $0}' tasker.private-key.pem
```

Переменные описаны в [Конфигурации](configuration.md#github-app). Нужно задать все шесть или ни одной: частичная настройка — ошибка запуска.

## Локальная разработка

GitHub App для `localhost` создаётся из админки так же, но без вебхука: привязка GitHub-аккаунта, подключение установок и ручная привязка PR работают, а события сами не приходят. GitHub не достучится до `localhost`, поэтому вебхуки пробрасываются туннелем (секрет вебхука при этом нужен свой — проще завести dev-приложение через переменные `GITHUB_*`):

```bash
# GitHub CLI (расширение): пересылает события репозитория на локальный адрес
gh extension install cli/gh-webhook
gh webhook forward --repo=owner/repo --events=pull_request,pull_request_review,push,create,delete,check_suite \
  --url=http://localhost:3000/api/webhooks/github --secret="$GITHUB_WEBHOOK_SECRET"
```

Другой вариант — [smee.io](https://smee.io): адрес канала указывается как Webhook URL приложения, а `npx smee-client --url https://smee.io/<канал> --target http://localhost:3000/api/webhooks/github` пересылает события локально.

Для входа и установки удобнее отдельное dev-приложение с `http://localhost:3000` в Callback и Setup URL.

## Вебхук

`POST /api/webhooks/github` обрабатывает запрос по шагам:

1. Интеграция не настроена → `404`. Тело больше 10 МБ → `413`.
2. Подпись `X-Hub-Signature-256` (HMAC-SHA256 сырого тела, сравнение за постоянное время) не сошлась → `401`.
3. Некорректные `X-GitHub-Event` или `X-GitHub-Delivery`, или тело не JSON → `400`.
4. Повторная доставка (`X-GitHub-Delivery` уже есть в `GithubWebhookDelivery`) → `200 {"result":"duplicate"}`.
5. Обработчик выполняется в транзакции → `200 {"result":"handled" | "ignored"}`. Ошибка → `500`: запись о доставке удаляется, доставку можно повторить в настройках GitHub App (**Advanced → Recent Deliveries**).

После коммита выполняются автосмена статусов, уведомления и обновление страниц пространства. Их сбой пишется в лог и ответ не меняет. PR обновляется, только если `updated_at` события не старше сохранённого: GitHub не гарантирует порядок доставки. Данные невыбранных репозиториев не сохраняются. Записи о доставках старше 7 дней удаляются по ходу работы.

## Частые проблемы

| Симптом | Причина |
|---------|---------|
| В настройках GitHub — «GitHub ещё не подключён к Tasker» | GitHub App не создан: администратор создаёт его в **Админка → Интеграции** (или задаёт `GITHUB_*`) |
| `/admin/integrations?error=state` | Ссылка создания старше часа или начата другим администратором |
| `/admin/integrations?error=failed` | GitHub не обменял код на ключи (код одноразовый и живёт час) — начните заново |
| Другие владельцы не видят своих аккаунтов при установке | Приложение создано без «Разрешить установку любым аккаунтам»: на GitHub → настройки приложения → **Advanced → Make public** |
| «Сначала привяжите GitHub в профиле» | Подключать установку может только владелец с привязанным GitHub |
| `?error=forbidden` после установки | Установка не видна пользователю в `/user/installations`: вошли в другой аккаунт GitHub |
| `?error=state` | Ссылка установки старше 10 минут или открыта другим пользователем |
| PR не привязывается | Репозиторий не выбран в пространстве, ключ не совпадает с ключом пространства или ссылка не на границе слова |
| Вебхуки отвечают 401 | `GITHUB_WEBHOOK_SECRET` не совпадает с секретом приложения |
| Логин GitHub в профиле недоступен | Токен отозван или истёк refresh-токен — привяжите GitHub заново |
