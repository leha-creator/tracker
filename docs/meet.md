# Связка с meet

Tasker и [meet](https://meet.plwedding.ru) связаны через общий вход plwedding ID: у пользователя в обоих приложениях один `sub`. Из задачи tasker можно начать созвон в meet; когда meet готовит конспект встречи, tasker сохраняет его заметкой в документах задачи. Поручения из конспекта можно превратить в подзадачи.

Этот документ — контракт для обеих сторон. Сторона tasker описана в [Архитектуре](architecture.md#связка-с-meet), сторона meet — в репозитории `leha-creator/meet`.

Брокера нет: tasker подписывает контекст задачи, meet подписывает вебхуки. Сервисных вызовов tasker → meet нет.

## Поток

```
Пользователь           tasker                                meet
    │ «Начать созвон»     │                                     │
    ├────────────────────►│ подписывает контекст задачи (ctx)   │
    │◄──── адрес ─────────┤                                     │
    │ GET <MEET_URL>/new?ctx=<токен> ──────────────────────────►│ вход через plwedding ID
    │                     │                                     │ проверяет ctx и sub, создаёт встречу
    │◄──────────────────────────────── редирект на /<code> ─────┤
    │                     │◄── POST вебхук meeting.created ─────┤ (с исходным ctx)
    │                     │ проверяет свою подпись ctx,         │
    │                     │ привязывает встречу к задаче        │
    │      … встреча, запись, конспект …                        │
    │                     │◄── POST вебхук meeting.ended ───────┤
    │                     │◄── POST вебхук recap.ready ─────────┤ (конспект JSON, без расшифровки)
    │                     │ заметка в документах задачи,        │
    │                     │ уведомление, журнал                 │
```

1. Пользователь нажимает «Начать созвон» в задаче. Tasker проверяет доступ к задаче и что пользователь связан с plwedding ID, подписывает контекст и открывает `<MEET_URL>/new?ctx=<токен>` в новой вкладке.
2. meet требует вход (через plwedding ID), проверяет токен и создаёт встречу, где организатор — вошедший пользователь. Тот же `jti` второй раз — та же встреча, а не новая.
3. meet шлёт tasker `meeting.created` с исходным токеном. Tasker доверяет только тому, что подписал сам: задача и пространство берутся из `ctx`, а не из полей события.
4. Конец встречи и готовый конспект — события `meeting.ended` и `recap.ready`.

## Контекст задачи (tasker → meet)

Формат: `<payload>.<signature>`, обе части — base64url без `=`.

- `payload` — base64url от JSON в UTF-8;
- `signature` — base64url от `HMAC-SHA256(MEET_CONTEXT_SECRET, "ctx." + payload)`.

Поля JSON:

| Поле | Тип | Значение |
|------|-----|----------|
| `v` | `1` | Версия формата |
| `iss` | `"tasker"` | Кто подписал |
| `aud` | `"meet"` | Для кого |
| `jti` | uuid | Идентификатор попытки: повтор с тем же `jti` — та же встреча |
| `sub` | string | `sub` пользователя в IdP — тот, кто нажал кнопку |
| `workspaceId` | uuid | Пространство tasker |
| `workspaceName` | string ≤ 100 | Для подписи встречи |
| `taskId` | uuid | Задача tasker |
| `taskKey` | string ≤ 32 | Ключ задачи, например `TSK-42` |
| `taskTitle` | string ≤ 300 | Название задачи на момент старта |
| `taskUrl` | URL | Страница задачи в tasker — ссылка «Вернуться к задаче» |
| `iat` | number | Время выпуска, Unix-секунды |
| `exp` | number | Срок, Unix-секунды: `iat + 600` |

Проверки на стороне meet (`GET /new?ctx=`), все обязательны:

1. Подпись — HMAC за постоянное время; другая длина — отказ.
2. `v = 1`, `iss = "tasker"`, `aud = "meet"`.
3. `exp` не прошёл (допуск на расхождение часов — 60 с).
4. Пользователь вошёл через plwedding ID и его `sub` (`Account.accountId` провайдера `plwedding`) равен `sub` из токена. Иначе — страница ошибки «Ссылка выдана другому пользователю», встреча не создаётся.
5. Встреча с этим `jti` уже есть — редирект на неё, без нового вебхука.

Неверный или истёкший токен — страница ошибки со ссылкой назад в задачу (`taskUrl`, только если подпись верна) и кнопкой «Обычный созвон». Значение токена в логи не пишется.

Встреча хранит `jti`, `taskKey`, `taskTitle`, `taskUrl`, исходный токен (до отправки `meeting.created`) и показывает в интерфейсе «Созвон по задаче TSK-42 · <название>».

## Вебхуки (meet → tasker)

`POST <TASKER_URL>/api/integrations/meet/webhook`, `Content-Type: application/json`, тело не больше 256 КБ.

Заголовки:

| Заголовок | Значение |
|-----------|----------|
| `X-Meet-Event` | `meeting.created`, `meeting.ended` или `recap.ready` |
| `X-Meet-Delivery` | uuid доставки; повтор той же доставки — тот же uuid |
| `X-Meet-Signature` | `t=<Unix-секунды>,v1=<hex HMAC-SHA256(MEET_WEBHOOK_SECRET, "<t>." + тело)>` |

Tasker проверяет подпись по сырому телу и отклоняет `t`, отличающийся от его часов больше чем на 300 с. Повтор доставки — новая `t` и новая подпись, тот же `X-Meet-Delivery`.

Ответы tasker:

| Код | Тело | Что делать meet |
|-----|------|-----------------|
| 200 | `{"result":"handled"}` | Готово |
| 200 | `{"result":"ignored"}` | Готово: событие не нужно tasker (задача в архиве, организатор потерял доступ, встреча неизвестна) |
| 200 | `{"result":"duplicate"}` | Готово: доставка уже обработана |
| 400, 401, 404, 413 | `{"error":…}` | Не повторять, записать в лог: ошибка формата, подписи или интеграция выключена |
| 5xx, таймаут, сеть | — | Повторить |

Повторы: экспоненциально (1 мин, 5 мин, 30 мин, 2 ч, 6 ч, 12 ч), всего до 24 часов, порядок событий одной встречи сохраняется — `recap.ready` не отправляется раньше, чем `meeting.created` получил 200. Таймаут запроса — 10 с.

### `meeting.created`

```json
{
  "meetingId": "0193…",
  "code": "abc-defg-hij",
  "url": "https://meet.plwedding.ru/abc-defg-hij",
  "hostSub": "oegotPMY5xbV1xSiVtySilJeIHnKQgzH",
  "createdAt": "2026-10-21T12:00:00.000Z",
  "ctx": "<исходный токен контекста>"
}
```

Tasker проверяет подпись `ctx` (срок `exp` здесь не важен, но `iat` не старше 24 ч) и `hostSub = ctx.sub`. Задача и пространство — из `ctx`.

### `meeting.ended`

```json
{ "meetingId": "0193…", "endedAt": "2026-10-21T13:00:00.000Z" }
```

### `recap.ready`

```json
{
  "meetingId": "0193…",
  "recapId": "0193…",
  "completedAt": "2026-10-21T13:05:00.000Z",
  "summary": {
    "overview": "…",
    "topics": ["…"],
    "decisions": ["…"],
    "actionItems": [{ "owner": "Анна", "task": "Подготовить макет", "due": "2026-10-28" }],
    "openQuestions": ["…"]
  }
}
```

`summary` — `RecapSummary` meet как есть: строки до 2000 символов, массивы до 50 элементов, `due` — дата `YYYY-MM-DD` или отсутствует. **Расшифровка в tasker не передаётся.** Встреча может дать несколько конспектов (несколько записей) — у каждого свой `recapId`.

Событие отправляется только для встреч, созданных по контексту задачи, и только после того, как `meeting.created` этой встречи получил 200.

## Переменные

| tasker | meet | Значение |
|--------|------|----------|
| `MEET_URL` | — | Origin meet: `https://meet.plwedding.ru` |
| `MEET_CONTEXT_SECRET` | `TASKER_CONTEXT_SECRET` | Общий секрет подписи контекста, не короче 32 символов |
| `MEET_WEBHOOK_SECRET` | `TASKER_WEBHOOK_SECRET` | Общий секрет подписи вебхуков, не короче 32 символов |
| — | `TASKER_URL` | Origin tasker: `https://tracker.plwedding.ru` |

Секреты генерирует владелец (`openssl rand -base64 32`) и кладёт копии в `/opt/tasker/.env` и `/opt/meet/.env`. В tasker все три переменные заданы или ни одной; без них кнопки и раздела нет, вебхук отвечает 404.

Порядок включения: сначала tasker (принимает вебхуки), затем meet (страница `/new` и отправка).

Ротация секрета: задать новый в обеих сторонах и перезапустить meet, затем tasker. Пока стороны расходятся, старт созвона и вебхуки отвечают ошибкой подписи, а вебхуки meet повторяет до 24 часов, поэтому ротацию делать в одно окно.
